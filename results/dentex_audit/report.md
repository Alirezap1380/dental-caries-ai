# DENTEX release audit

Generated by `scripts/audit_dentex.py` from the HuggingFace release (`ibrahimhamamci/DENTEX`). Zip sources: test_data.zip (local), training_data.zip (remote), validation_data.zip (local). DENTEX: Hamamci et al., arXiv:2305.19112, CC-BY-NC-SA 4.0. Counts and file names only.

## Layout and annotation formats (check 4)

| subset | images |
|---|---|
| (a) quadrant | 693 |
| (b) enumeration | 634 |
| (c) diagnosis train | 705 |
| unlabelled | 1571 |
| validation | 50 |
| test | 250 |

- Subsets (a), (b), (c)-train: COCO JSON, one file per subset inside `training_data.zip`.
- Validation: images in `validation_data.zip`; labels in a *separate* COCO file `validation_triple.json` at the repository root.
- Test: LabelMe JSON, one file per image (`disease/label/test_*.json`), polygon labels `code-word-FDI`. Vocabulary: {'0-saglam': 91, '1-çürük': 747, '2-küretaj': 265, '3-kanal': 161, '5-çekim': 29, '6-gömülü': 221, '7-lezyon': 75, '8-kırık': 11}.
- Junk to skip: ['validation_data/quadrant_enumeration_disease/xrays/.ipynb_checkpoints/val_0-checkpoint.png'].
- Category ids are NOT positional. In (a), quadrant id 0 is named "2" and id 1 "1". In (b), names are ints; in (c), strings. Map through the names, never `id + 1`.
- File names are reused across subsets for *different* images (e.g. `train_673.png` in (a) and (c) have different dimensions), and the same image appears under different names. Identity must come from content, not names.

## Does (c) enumerate every tooth? (check 1)

No. (c) boxes only diagnosed teeth: median 4 boxes per image (max 23; 27 images with none), against a median of 29.0 per image in (b), which boxes every tooth. An inventory rebuilt from (c)'s boxes is diseased-teeth-only, and `check_inventory` **fires**, as it should.

Of the diagnosis-train images that also appear in (b), 242 have a (b) enumeration containing every diagnosed tooth: a usable human inventory (median 29.0 teeth, 83.5% carrying no finding). 18 more have a diagnosed tooth whose FDI number is missing from (b)'s enumeration, so the two annotation layers disagree on numbering there. (b) itself has 16 images with a duplicated FDI and 2 with more than 32 boxes.

## Were the test labels released? (check 3)

Yes (250 label files), but **not as the challenge's 4-class diagnosis ground truth**. The released test labels use an 8-code Turkish vocabulary that reads as treatment-oriented. The official evaluation script reads COCO ground truth with `category_id_1/2/3`, which is not in this release. Test codes against train diagnoses, by tooth region:

| label | n | incisor | canine | premolar | molar |
|---|---|---|---|---|---|
| test 0-saglam | 91 | 26% | 13% | 26% | 34% |
| test 1-çürük | 747 | 4% | 2% | 21% | 72% |
| test 2-küretaj | 265 | 55% | 9% | 10% | 26% |
| test 3-kanal | 161 | 3% | 6% | 19% | 73% |
| test 5-çekim | 29 | 7% | 0% | 28% | 66% |
| test 6-gömülü | 221 | 0% | 0% | 0% | 100% |
| test 7-lezyon | 75 | 27% | 5% | 19% | 49% |
| test 8-kırık | 11 | 82% | 18% | 0% | 0% |
| train Caries | 2189 | 5% | 3% | 24% | 68% |
| train Deep Caries | 578 | 4% | 1% | 22% | 73% |
| train Impacted | 604 | 0% | 0% | 0% | 100% |
| train Periapical Lesion | 158 | 22% | 5% | 22% | 51% |

`çürük` (caries), `gömülü` (impacted) and `lezyon` (lesion) match their train counterparts by region. `küretaj` (curettage) sits mostly on incisors, unlike deep caries, and fits periodontal treatment. `kanal` (root canal) matches deep caries' region pattern but is a treatment code (possibly an existing filling). The image present in both train and test shows the two schemes side by side:

| image | labels (FDI: label) |
|---|---|
| `train_332.png` (train) | 16: caries, 18: deep_caries, 26: caries, 27: caries, 28: deep_caries, 45: caries, 46: deep_caries, 47: caries |
| `test_181.png` (test) | 16: 1-çürük, 17: 7-lezyon, 18: 3-kanal, 26: 3-kanal, 28: 5-çekim, 31: 2-küretaj, 41: 2-küretaj, 46: 7-lezyon, 46: 5-çekim, 47: 1-çürük |

**Consequence:** no defensible deep-caries label exists on the released test set. The depth-stratified labelled set is (c)-train + validation = 755 images (before removing duplicates). Test can contribute only through a versioned mapping like the Tufts one, for classes that map unambiguously.
