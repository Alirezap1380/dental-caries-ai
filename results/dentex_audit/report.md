# DENTEX release audit

Generated by `scripts/audit_dentex.py` from the HuggingFace release `ibrahimhamamci/DENTEX`. Each zip was verified against its published SHA-256 before reading. DENTEX: Hamamci et al., arXiv:2305.19112, CC-BY-NC-SA 4.0. Counts and file names only.

## Layout and annotation formats (check 4)

| subset | images |
|---|---|
| (a) quadrant | 693 |
| (b) enumeration | 634 |
| (c) diagnosis train | 705 |
| unlabelled | 1571 |
| validation | 50 |
| test | 250 |

- Subsets (a), (b), (c)-train: COCO JSON, one file per subset inside `training_data.zip`.
- Validation: images in `validation_data.zip`; labels in a *separate* COCO file, `validation_triple.json`, at the repository root.
- Test: LabelMe JSON, one file per image (`disease/label/test_*.json`); labels `code-word-FDI`. Vocabulary: {'0-saglam': 91, '1-çürük': 747, '2-küretaj': 265, '3-kanal': 161, '5-çekim': 29, '6-gömülü': 221, '7-lezyon': 75, '8-kırık': 11}.
- Junk skipped by the loader: ['validation_data/quadrant_enumeration_disease/xrays/.ipynb_checkpoints/val_0-checkpoint.png'].
- Category ids are not positional. Quadrant categories in (a): id 0 = "2", id 1 = "1", id 2 = "3", id 3 = "4". The loader maps every id through its name.
- File names are reused across subsets for different images, and the same image appears under different names. Identity comes from content (SHA-256).

## Does (c) enumerate every tooth? (check 1)

No. (c) boxes only diagnosed teeth: median 4 boxes per image (max 23; 27 images with none), against a median of 29.0 in (b), which boxes every tooth. An inventory rebuilt from (c)'s boxes is diseased-teeth-only, and `check_inventory` **fires**, as it should.

Evaluation images (diagnosis train + validation) with a human inventory from a byte-identical copy in (b): **253** (median 29 teeth; 83.9% of teeth carry no finding). Excluded from tooth-level metrics despite a (b) copy: 17 because a diagnosed tooth's FDI number is missing from the enumeration; 1 because copies in the enumeration subset disagree; 7 because an FDI number is boxed twice in the enumeration subset.

## Were the test labels released? (check 3)

Yes (250 label files), but **not as the challenge's 4-class diagnosis ground truth**. They use an 8-code Turkish vocabulary that reads as treatment-oriented. The official evaluation script reads COCO ground truth with `category_id_1/2/3`, which is not in this release. Test codes against train diagnoses, by tooth region:

| label | n | incisor | canine | premolar | molar |
|---|---|---|---|---|---|
| test 0-saglam | 91 | 26% | 13% | 26% | 34% |
| test 1-çürük | 747 | 4% | 2% | 21% | 72% |
| test 2-küretaj | 265 | 55% | 9% | 10% | 26% |
| test 3-kanal | 161 | 3% | 6% | 19% | 73% |
| test 5-çekim | 29 | 7% | 0% | 28% | 66% |
| test 6-gömülü | 221 | 0% | 0% | 0% | 100% |
| test 7-lezyon | 75 | 27% | 5% | 19% | 49% |
| test 8-kırık | 11 | 82% | 18% | 0% | 0% |
| train caries | 2189 | 5% | 3% | 24% | 68% |
| train deep_caries | 578 | 4% | 1% | 22% | 73% |
| train impacted_tooth | 604 | 0% | 0% | 0% | 100% |
| train periapical_lesion | 158 | 22% | 5% | 22% | 51% |

`küretaj` (curettage) sits mostly on incisors, unlike deep caries, and fits periodontal treatment. `kanal` (root canal) and `çekim` (extraction) are treatment codes. The image(s) present in both train and test show the two schemes side by side:

|---|---|
| `train_332.png` (train) | 16: caries, 18: deep_caries, 26: caries, 27: caries, 28: deep_caries, 45: caries, 46: deep_caries, 47: caries |
| `test_181.png` (test) | 16: 1-çürük, 17: 7-lezyon, 18: 3-kanal, 26: 3-kanal, 28: 5-çekim, 31: 2-küretaj, 41: 2-küretaj, 46: 7-lezyon, 46: 5-çekim, 47: 1-çürük |

**Consequence:** the released test set has no evaluation role in this project (see README). The depth-labelled evaluation set is diagnosis train + validation = 755 images.
